# 项目执行经验与控制要点

更新：2026-10-24。面向后续开发 Agent 和维护人员。规则入口是仓库根目录 AGENTS.md；当前批次顺序以《后续推进计划与执行要求》为准。本文件整理已观察到的问题与可复用处理方法，不新增产品范围或验收门禁。

## 1. 怎样开始和结束一个批次

先读取仓库规则、最新计划和工作区，确认目标仍有效。用户说“继续”时接续当前已授权范围，不重启旧的全量验收队列。

批次开头用下列几行即可：

- 本批结果：用户最终能操作或看到什么。
- 变化与验证：改哪个层，用什么最小失败用例验证；文档和低影响样式无需形式化红灯。
- 可复用项：现有候选、构建、基线、服务、回归脚本。
- 资源退出：哪些临时目录/部署会停止或回收，哪些产物需要保留。
- 停止条件：哪些证据满足后提交并交付，哪些内容留到下一批。

完成时报告用户可用变化、实际检查、边界、调用/编译/打包次数、资源变化、提交 SHA 与下一项。未知耗时不能填零。显式 goal 只覆盖约定阶段，完成后结束；下一阶段另行启动。

## 2. 曾经拖慢交付的做法

| 观察到的问题 | 后续处理 |
| --- | --- |
| 为看 Demo 先逐条刷新完整 TD-15 | 先交付固定样例闭环；完整阶段验收作为独立批次 |
| 文案、报告或用例变化触发全量 Docker 构建 | 按实际变化层验证；需要部署时只构建受影响服务一次，复用镜像做多项测试 |
| 同内容被不同 jobId、runId 反复打包 | 按 RP-02 分离内容与执行身份；变更前仍如实记录旧路径 |
| 每次生成或测试复制完整 SDK/JAR | 优先复用既有候选；共享依赖与回收机制按 RP-02 实现，不无限保留临时工程 |
| 网络/观察超时就重新开始整条流程 | 检查原任务的真实状态，继续轮询同一 ID，终态后再决定后续处理 |
| 开发失败就降低独立验收预期 | 修改缺陷所在层；开发单测可纠错并留差异，独立基线及硬性断言保持原意 |
| “工具调用成功”被当成业务成功 | 核验实际接口结果、数据库/Mock 状态、文件和候选摘要 |
| 为清理空间笼统删缓存、所有镜像或进程 | 按归属和引用筛选精确清单；说明逻辑回收量与宿主机实际可用空间的差别 |

## 3. 已验证的具体教训

### RP-01：输出格式也是运行契约

首次选择历史真实生成候选时，工具返回了正确设备事实，但 Agent 输出自然语言，不满足既有 equipment-report/clarification JSON 断言。保留失败报告，改选现有兼容模板，之后完成正常查询、缺参、超时、发布和业务对话。没有为演示降低断言，也没有重新生成或编译。

可复用方法：选择样例前同时核对 SDK/制品可装载性、业务输出契约与验收基线；“曾经运行成功”不能推断“现在可发布”。模板样例必须显示来源，不能宣称双 Agent 已为本次需求自动生成。

### 浏览器失败：先确认真实操作卡在哪一步

RP-01 曾停在输入框定位。为需求与业务输入补明确的可访问标签后，继续使用原验收报告和原发布版本完成操作。不能因为 UI 定位失败重新生成组件或重跑已完成业务步骤。

可复用方法：动作超时设置合理上限，记录最后完成阶段；优先使用明确的角色/可访问名称定位。后续 UI 恢复检查可以复用已经完成的真实验收，无需再次调用模型。

### Docker 清理：空间数字不能相加

2026-10-24 本批清理 Docker 报告回收 16.7 GB；容器状态与镜像引用保持一致、主服务健康。Windows 的 VHDX 文件大小未缩小，D 盘实际可用空间未明显增加。镜像与构建缓存共享层，不能把两项变化相加当作释放量。

可复用方法：记录前后状态、实际删除对象和 Docker 返回值。虚拟磁盘压缩是另一项维护操作，涉及服务可用性，不能把镜像清理自动扩大成停机或删除虚拟磁盘。

## 4. WSL 接续环境

- 当前工作仓库：Ubuntu-24.04 的 /home/vincent/agent-builder-java。后续以它为开发入口，不同时维护 Windows、WSL 两套活跃开发目录。
- Windows 原仓库为 D:\agent-builder-java，迁移时保留，不能在未核对前删除。
- 迁移前两端代码均为 146b26c；已按原字节迁移 .env.local 和 21 个未提交证据文件，模型为 deepseek-v4-flash。Key 在 .env.local，不在本文件；OpenCode 开发角色通过同一环境变量读取。
- 迁移只证明文件一致；不等同于新环境已安装全部依赖、模型联通或完成新验收。已有证据保留原目标与原环境。
- Windows 的 Vite/启动器/esbuild 已关闭；Docker Desktop 和容器保持运行。启动新前端前先检查监听，不同时起 Windows 与 WSL 两份。
- WSL 的 Node/pnpm/Git 使用 Linux 版本；不要把 Windows 的 node_modules、.cache、历史测试目录或二进制整包搬过来。
- 复用 Docker Desktop 的 WSL Integration。docker ps 应能看到已有项目容器；不要另装独立 Docker Engine 或通过另一项目名重复创建主环境。
- 主后端目前端口为 18080，已发布样例依赖原候选和数据卷。WSL 到宿主机 localhost 的连通取决于实际网络模式，先验证再配置；不要为联通随意放宽 Origin/审批/鉴权。
- 迁入的 .env.local 按源文件保留，可能含 Windows 浏览器配置。Linux 浏览器检查前确认 PLAYWRIGHT_CHANNEL 与实际安装匹配；不能因迁移就默认 Windows Edge 可用。
- 只展示环境变量名或“已配置/一致”；不要执行会把整个环境配置、Key 或令牌打印出来的排查命令。

## 5. 后续推进边界

RP-01 已交付的是预构建只读模板样例。下一项 RP-02：内容身份、构建复用与资源回收。RP-03 负责 Skill 增量装载；之后再推进场景边界、真实双角色与四类产物。不要用环境迁移替代这些实现，也不要让迁移变成无限前置工程。

## 6. 复用到其他项目

可直接复用第 1、2 节的批次方法，以及第 3 节的诊断方式。第 4 节的路径、端口、提交和迁移结果仅属于本机快照，使用前必须重新核验；不要将这些值复制成其他项目的固定要求。
