目标客户是类似大型银行 AI 平台部门的开发人员。客户画像来自项目需求定义；当前尚未提供外部客户试点数据。

01

需求与实现容易脱节

设计要解决的问题：需求文字、实现版本和测试依据分散，结果难以复核。

产品响应
确认需求修订、冻结基线与快照，把验收结论绑定到候选。

可观察结果：从报告定位需求、源码和实际制品。

02

生成代码仍需测试与集成

设计要解决的问题：代码生成后，还需准备运行环境、测试数据和企业接口。

产品响应
开发／测试角色协作，统一执行器，提供独立 Mock 环境。

可观察结果：同一入口完成生成、预览、回归与演示发布。

03

“回答成功”不足以证明执行正确

设计要解决的问题：模型声明完成，可能没有产生正确结果或真实工具调用。

产品响应
程序断言、实际 HTTP 调用、业务状态与版本绑定共同验收。

可观察结果：每项通过或失败都有可检查的事实依据。

收益是待验证假设：一站式流程有望降低开发与测试交接成本；需用固定任务包比较交付成功率、耗时和人工介入，当前不宣称效率提升百分比。

需求来源：PRD：客户、产品范围与指标固定任务包与评测口径

04 / DELIVERY WORKFLOW

两个 Agent 参与开发，平台依据证据作最终验收

独立性来自固定输入、角色权限、测试环境和事实检查。当前流程为有序协作，测试方案先于业务实现形成。

02 →

03 →

单测红灯 → 实现 → 绿灯；生成 Tool 与 Skill。

04 ↓

05 →

06 →

平台评定报告

核对断言、外部事实与绑定。证据不足不判通过。

07 →

同一制品准备新实例，通过冒烟再切换演示入口。

08 ✓

模拟 App 验证结果

独立业务身份调用，核查版本与实际外部动作。

平台／用户控制点模型工程角色
追溯链需求修订→基线／快照→工程包／测试计划→候选 JAR→Run／外部证据→报告／发布版本

失败分支：完整失败报告 → 用户启动修复 → 冻结旧方案与测试 → 新回归测试复现 → 新候选全量回归。当前不支持无人值守的任意需求自循环。

实现依据：双角色生成候选报告与同制品发布有限修复

05 / SYSTEM ARCHITECTURE

TS 管交付流程，Java SDK 执行业务 Agent

采用 TypeScript 模块化单体与独立 Runner。持久化业务流程、工程进程和 Agent 执行各有明确归属。

React → 平台 app → Runner
平台持久化交付流程，Runner 管理工程进程与 JVM。

Runner → OpenCode / Java Bridge
工程角色生成代码；Java SDK 执行业务 Agent。

Java → 平台 Tool Proxy → Mock → Mock 库
在实际调用路径执行动作检查，业务事实保存在 Mock。

平台库 + Runner 卷
分别保存流程状态、固定制品与工程证据。

平台：持有需求、验收、发布、业务请求与平台 Run 状态；以数据库事务与版本绑定维护交付一致性。SDK 内部执行状态由 Java Runtime 管理。

源码：平台组装Runner 组装ComposeCore 0.1.17 / Runtime 0.1.4 固定提交

06 / DESIGN CHOICES & TDD

把“代码生成”变成有失败反馈、有版本约束的工程过程

技术特点体现在可检查的机制，而非模型自评。平台开发本身与平台内自动开发，均保留针对行为的测试证据。

设计选择解决的问题与机制可核验结果／边界
测试先行先固定方案；单测在初始实现上真实失败，再修改代码。命令、退出码、红绿结果可审阅；不以编译失败充当缺陷复现。
固定制品贯穿交付源码、测试计划、JAR、报告与版本建立绑定。发布复用已验收 JAR；旧报告不能为新制品放行。
独立环境 + 外部事实逐用例部署，使用 test-api，核对 Mock 实际调用与数据。模型只说“完成”不足以通过。当前只读三项、工单模板八项。
持久化流程 + 有界执行请求去重、任务租约、过期执行者回写拒绝、取消和预算。保留状态与证据；完整 JVM 会话恢复与孤儿进程治理仍待完善。
修复机制已验证

旧代码先复现，新代码再回归

保留原失败报告、测试方案及旧单测。新增回归测试在旧代码上取得断言红灯后，才允许修改实现。修复包生成新候选，重新运行全部基线。

最多 3 次修复 / 初始任务900 秒 / 次
OBSERVED CASE / TDD-016

Mock 是 86℃，缺陷实现报告 87℃

独立事实断言检出偏差。真实 OpenCode 生成回归测试并修复，三项验收通过，发布同一新 JAR 后业务请求成功。

证据条件：起点是明确标注的预置缺陷；修复角色与业务 Agent 使用真实 DeepSeek，不能称作首轮自动生成成功。

红灯、修复与回归记录平台 TDD 计划受限路径／命令接口与独立角色会话不等于文件系统／进程沙箱。

01 · 确认需求并冻结定义

页面操作

填写三个需求字段并逐项确认，保存草稿。选择“设备状态查询”，审阅并确认验收基线，再点击“固定为测试版本”。

核验点

存在已确认基线和新快照。调试消息可输入“查询 PUMP-001 的状态、温度与来源。”，检查实际外部调用。

操作顺序：确认需求与基线 → 启动双角色开发 → 选择生成构建、登记候选 → 指定候选运行验收 → 审阅并发布 → 模拟 App 新建会话调用。失败时按证据修复，登记新候选后重新验收。

完整操作步骤、维护、接口与排错新人快速上手模型显示“已配置”不等于调用已经验证成功；首次构建时间取决于网络和机器。

10 / NEXT REVIEW

下一步先补齐交付范围，再测量端到端成功率

以下顺序是建议，供团队评审确定；不构成交付日期、负责人或成功率承诺。

A

补齐业务闭环

Agent／Rail 与写组件自动生成；金融 API → Skill → Agent → App 联调；扩展写结果核对。

完成依据
对应基线的正常、异常、审批和幂等分支均有真实证据。

B

补齐交付与恢复

变更分析、导入导出、全新目录部署、运行中崩溃与孤儿进程核对、性能回归。

完成依据
版本、制品和业务状态可复核，完整必测集合达到阶段要求。

C

运行固定任务评测

固定需求包、重复次数和预算，从干净工程与数据开始；登记全部尝试和人工介入。

完成依据
给出成功数／任务数、状态分布、耗时与辅助交付，形成首轮基线。

交付成功率 = 预算内通过验收的任务尝试数 ÷ 全部已启动任务尝试数

失败、超时、取消、阻塞与未验证保留在分母；预算内自动修复仍算同一次尝试，人工直接修补代码／测试的辅助交付单列。尚未终结的任务只能形成中间结果。

建议本次团队评审确认三件事

① 选择下一轮优先业务场景及其业务接口责任人。
② 明确开发、独立测试与环境维护的承担者，以及模型／验证资源。
③ 在评测前冻结任务包、重复次数、预算和成功口径，首轮测量后再讨论目标值。

评测定义与任务包剩余工作包首期保持可信本地模式；生产托管、多租户与沙箱不作为本轮已完成能力。
