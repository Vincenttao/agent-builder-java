# 技术设计复审与轻量化方案

日期：2026-10-24。范围：本地 agent-builder-java 的交付节奏、测试成本、运行资源和磁盘生命周期。

状态：架构决策已确认采用，实施顺序与要求见[后续推进计划](后续推进计划与执行要求.md)；业务改造尚未实施。未清理历史数据，未执行构建或回归。本文不将 Demo 等同于完整 PRD 验收。

## 结论

本版以架构决策替换前两版优化建议，作为后续实施依据；不缩减 PRD 产品范围，不将未验证能力记为通过。

### 架构决策摘要

**选择：保留现有技术栈与 API，以“可复用业务内容 + 独立执行记录”改造生成与验证路径。固定样例演示先复用已有可信产物，完整外部组件加载不作为首个 Demo 的前置条件。**

| 方案 | 能解决什么 | 代价与缺口 | 决策 |
| --- | --- | --- | --- |
| 只加缓存、清文件 | 缓解占用 | 执行 ID 仍污染产物身份，场景仍耦合核心，真实生成仍在关键路径 | 只作止损 |
| 保留现有 API，分离内容/执行身份，增加增量路径 | 可复用构建，减少模型调用，保护已有 UI、审批、持久化工作 | 要改生成包、候选清单、运行清单契约，并兼容旧格式 | 采用 |
| 改成新的通用工程平台，全面重写 Runner/存储/调度 | 可能获得更完整的通用能力 | 新平台的范围与验证成本不可控，延迟 Demo | 本轮不采用 |

#### 已核验的首要设计缺陷

`EngineeringWorkspace` 把 `unitRedId/unitGreenId/contractCheckId/buildId/snapshotId/baselineId` 纳入 Bundle 摘要。`RuntimeArtifactRegistry` 再把这个摘要与快照写入完整 JAR，且以 `bundleDigest + specDigest + sdkArtifactDigest` 作为打包复用键。即使源文件与依赖相同，不同执行也会产生不同 Bundle 和完整 JAR。缺少清理会放大占用，但仅补清理无法修正这个身份模型。

建议分为四种身份，值变化仅使依赖它的工作失效：

| 身份 | 内容 | 不纳入的内容 |
| --- | --- | --- |
| 编译输入键 | 生产源码、编译器/选项、SDK/依赖实际摘要、生成模板版本 | jobId、测试执行 ID、测试日志、需求快照 ID |
| 候选内容摘要 | 编译产物、Skill/配置、接口与 Rail 绑定、Runtime 实际摘要 | runId、报告时间、发布操作 ID |
| 验证输入摘要 | 候选摘要、测试/断言版本、Mock 数据/故障、模型配置及相关执行器契约 | 页面资源、无关日志、上次执行 ID |
| 执行记录 ID | 本次输入摘要、角色记录、命令、耗时、结果与证据 | 不作为被测程序的内容来源 |

编译输入键用于寻找缓存，命中后仍校验实际输出摘要。构建还需规范归档时间等非业务输入；不能假设现有 JAR 命令天然可复现。验收计划与需求基线保存在候选的审阅/验证关联中；同一代码可被新基线重新验证，不需要把基线编号打进可执行 JAR。模型配置相同也不保证实时服务输出完全一致，因此可复用确定性构建，不可据此伪造一次新的真实模型评测。

#### 双角色保留，机械工作退出模型循环

开发侧先输出可审阅的变更计划：复用哪些资产、修改哪些文本/配置、哪些确需新代码。稳定 HTTP 参数校验、字段映射和 SDK 调用外壳优先由已审阅模板物化；业务逻辑和新的扩展代码才进入模型编码。模板产物与模型产物分别记录来源，四类真实生成仍需真实案例证明。

测试侧先制定验收计划，确认后由普通执行器运行。代码作者可以修正自己的单测，但不能修改独立验收条件。无变化的需求不重复让测试 Agent 抄写原计划；无变化的源码不重复生成或编译。

#### 修改 Skill 的目标调用链

当前路径：新任务 → 两个角色 → Java 单测/编译 → 完整 JAR → 逐用例测试部署 → 发布。

目标路径：生成或编辑 Skill → 校验内容及依赖 → 新候选清单引用原编译组件 → 验证受影响行为 → 本地演示入口切换。没有 Java 源码变化，就不执行 javac，也不修改工具链。

首个固定样例演示可直接采用可信的预构建候选，生成新执行记录、重置业务数据并真实验证；显示“样例”，不伪造 OpenCode 会话或新构建记录。后续用同一个候选契约接真实生成器。

#### 物理边界和测试隔离

保持当前四类服务：平台 App、Runner、Mock、PostgreSQL。Runner 负责短期构建和 Java 子进程；不新增微服务。开发时 App/Web 可用已有本地入口启动，基础环境复用；仅部署验证或对应服务输入变化时重建镜像。

已有测试部署具备 TTL、过期停止和活动数上限 4（`test-deployment-service.ts`）。此前“需要增加租期”的表述不准确，应改为验证停止后的资源回收及恢复策略。已有 Java HTTP 测试也具备确定性模型服务，不应重新造一套替身系统。

当前候选验证逐用例创建部署。先复用制品与 SDK，再评估同候选的顺序只读用例能否复用一个 JVM；只有能证明会话/Mock 状态独立、取消与异常无残留时才启用。写入、崩溃与恢复用例继续隔离，不能用盲目复用换速度。

#### 最小迁移与回退

1. 固定当前版本与证据作为 legacy 路径，不回写其摘要。新增格式标识，旧候选按旧格式读取和运行。
2. 先把内容摘要与执行记录分开，单测证明两次执行同一内容只保留一份编译产物；任一源码/依赖变化必须失效。只移动业务身份，不删除验收关联。
3. 接入可信预构建样例，走现有 API、实际 Mock 与演示入口；先交付可操作闭环，不等通用工程平台。
4. 在新格式下实现 Skill 外部装载和组件复用；无法装载时显式保留 legacy 单份 JAR 路径，不假报增量执行成功。
5. 用第三个相似业务项目检查场景边界，再扩展代码生成。新版失败时切回旧格式入口；不修改正在执行任务的绑定，不做破坏性数据库迁移。

每批完成一项可观察行为后提交。先做轻量测试和有关适配验证，最后集中做一次必要部署验证；不为每个断言重建环境。不得以“架构整改”为由先建设新的缓存平台、回收平台、插件市场或统一工作流引擎。

#### 判定整改有效的证据

- 同一内容连续执行三次：编译/打包次数不随执行次数增长，执行记录仍各自存在，磁盘只增加限定的结果数据。
- 只改 Skill：Java 编译次数为 0，行为测试使用新 Skill，旧版本仍可回滚。
- 改 Tool 源码：该组件重编译，相关测试重跑，SDK 不复制或重建。
- 改 UI：不调用生成模型、不构建 Java、不重跑无关业务用例。
- 新增一个已支持接口形态的查询场景：无平台业务分支、无 Dockerfile 改动；接口超出支持边界时明确报缺口。
- 生成和验证各阶段记录排队、模型/角色、编译、启动、业务运行、证据整理耗时。不能将总任务时间减去编译时间就全称为模型推理时间。

旧模型下的磁盘快照只证明存在重复文件，尚未量化每类改造的时间收益。以上计数与状态验证通过后，再报告冷/热执行耗时与空间差值；不提前承诺倍数或整项目工期。
