## 1 目标与交付边界

后续产品主线为“平台开发者交付范式/模板 → 场景开发者配置与少量开发 → 企业 CI/CD 交付”。以 MOA 类范式和 i豆为贯穿案例，先完成模板接手、查询与映射修复切片，再扩展受控兑换和独立服务交付。AI Coding 按需使用，真实双角色生成不再是每次场景开发的前置条件。

复用 TS 平台、Java 执行底座和已有版本/验收机制。四页签继续承载现有 Demo；新 PRD 的五个应用工作区按受影响批次实现，不因更新设计立即重写全部界面。身份分离、构建复用和资源回收按实际影响接入，不能成为首个场景切片的通用架构前置条件。

区分三种交付：

| 交付 | 可以说明什么 | 不能说明什么 |
| --- | --- | --- |
| 样例 Demo | 工作台、真实候选运行、业务 Mock、验收和本地演示流程可用 | 双 Agent 已自动完成新需求 |
| 架构整改 | 同一内容可复用，修改范围决定构建/测试范围，资源可回收 | 完整 PRD 已验收通过 |
| 产品阶段交付 | 指定 PRD 版本及该阶段的业务/交付能力已由对应证据验证 | 未实现的后续阶段或另一个 PRD 基线已完成 |

本次只新增 PRD 2.0 并同步导航、计划和进度入口，不修改旧机器清单摘要，不恢复逐条刷新 TD-15 证据的旧队列。RP-01 已交付，实际结果见 [RP-01 实施记录](implementation/RP-01.md)。文档完成后停止本批，不自动开始 i豆开发。

## 3 日常执行要求

1. 每批只解决一个可观察问题。开工先写“变化对象、最小失败用例、预计触及的构建/测试层、资源退出方式”；用几行批次记录即可，不另建审批流程。
2. 平台行为修改继续 TDD。文档、低影响样式不为形式编写测试。代码缺陷在组件层复现，Skill/提示缺陷在内容或行为层复现，不人为制造无关 Java 红灯。
3. 开发 Agent 的单测允许纠错并记录差异；独立验收基线及硬性断言不可由开发 Agent 降低。既有回归测试的业务预期不能因实现失败而被削弱。
4. 测试 Agent 在需求或验收条件变化时设计/更新方案，稳定回归由执行器运行。平台机械校验、已审阅模板物化和不变组件复用不必调用模型。
5. 失败分为实现、测试脚本、模型行为、环境/依赖四类，修复对应层；环境故障不生成新的业务代码。默认不自动重跑整个批次，不隐藏失败尝试。
6. 不因用例切换、报告刷新、文档修改或存储位置迁移重建 Docker。服务构建输入变化且需要部署验证时，只构建受影响服务一次，在同一镜像上批量测试。
7. 历史证据保留原目标。修改发生后先跑受影响检查，暂不重跑无关检查；这不代表旧报告已成为新目标的正式通过记录。
8. 每个完整功能/修复批次完成必要检查、审阅差异后本地提交；不夹带旧证据、缓存、密钥或其他修改。不自动推送，不以 GitHub CI 作为本地推进阻塞条件。

## 4 变更与检查矩阵

以下是日常开发规则，不是每次提交都执行的全套清单。

| 变化 | 必要检查 | 默认无需执行 |
| --- | --- | --- |
| 文档、计划 | 内容一致性、链接、diff；机器清单摘要变更时运行对应一致性检查 | 程序测试、模型、Docker |
| UI 文案/样式 | 相关视图/构建按实际影响；流程变化补相关浏览器检查 | Java 编译、生成模型、全量业务回归 |
| 平台规则/API/数据库 | 受影响单元/契约、类型检查；涉及事务时定向真实 DB 集成 | 无关场景生成、全量镜像构建 |
| Skill/Agent 提示/已有 Rail 参数 | 内容和引用校验、装载、相关行为检查；语义变化选必要真实模型样本 | 无变化的 Java 源码编译、SDK 重建；RP-03 前保留实际旧路径并记录偏差 |
| Java Tool/Agent/Rail 源码 | 组件编译、单测/契约、真实装载与相关业务用例 | 无关 UI、SDK 重建、所有任务重新生成 |
| 生成器/提示/模板 | 确定性契约 + 相关真实生成样本，保留失败 | 全量平台故障注入 |
| SDK/Bridge/运行契约 | 对应适配测试、代表性真实集成；影响未知时扩大相关检查 | 自动重新生成全部业务工程 |
| Compose/镜像/配置 | 对应服务构建或配置检查、启动冒烟；持久化变化才增加恢复测试 | 每次都执行全部 NFR |
| 正式阶段交付 | 阶段累计集合和有效证据覆盖；单独锁定批次 | 每个小提交提前执行同一完整集合 |

现有命令见 `package.json`；可用 Vitest 文件过滤执行定向集合。不要引用尚不存在的 lint、contracts:check 或评测命令作为必须通过的检查。

## 5 证据复用与门禁过渡

正式检查器目前仍有整体镜像绑定约束，文档更新不会自动改变检查器。过渡期间分开输出“本批受影响检查结果”和“现有正式阶段报告”，未迁移的旧证据不改摘要、不冒充当前验证。

此前 RP 计划刷新已同步 `tests/acceptance/manifest.json` 的文档基线摘要，88 个验收条目及其分支不变；历史报告继续绑定其原基线。**本次 PRD 2.0 不修改该清单、旧 PRD 或旧测试基线。** 2.0 的新增验收编号另行落地，不能靠摘要同步宣布重新验收。

新增证据复用机制时，必须记录来源报告、原/现目标、变化文件/契约、适用条件、复用理由及实际环境；验证相关依赖变化会使结果失效，不相关变化不会误失效。无法证明影响范围时，扩大相关测试，不直接判定复用。

完整阶段交付仍覆盖所声明 PRD 版本的全部阶段必需项；可复用的证据是否计入，通过已实现、测试过的规则裁定。真实模型评测始终保存本次调用与全部任务尝试，不能通过缓存一次成功结果提高成功率。

## 6 磁盘与进程要求

- 新增测试从第一批就有退出清理；成功保留报告/必要日志，临时解包与打包副本退出时回收。失败诊断按有限数量/体积保留，不无限复制 SDK。
- SDK 按实际内容版本共享；候选按内容引用。已发布、回滚保留、活动任务、明确保留证据所需产物不因清理阈值被删除。
- 测试部署已有 TTL、过期停止和活动上限；复用这些机制，补停止后的文件回收。只恢复需要继续服务的明确目标，不为历史测试记录启动 JVM。
- 仅维护一套主开发环境；破坏性测试临时环境结束后回收其自有资源。当前遗留环境先核对归属和引用，不能仅凭名称批量删卷。
- 历史清理先生成精确路径、用途、大小和保留项清单；只有已授权且核实可回收的目录才执行删除。禁止全局卷清理，也不直接删除 Docker VHDX。
- RP-02 验收连续执行三次的磁盘变化：大型依赖/编译产物不随次数增长，新增内容限于可解释的执行记录；不能以“测试通过”掩盖几十 GB 残留。

## 7 每批汇报与排期

每批汇报：用户可用的变化、实际完成的检查、未验证边界、模型调用/编译/打包次数、相关磁盘差值、提交 SHA、下一项。无关指标标“不适用”，未知耗时不得填零。

耗时按排队、生成角色/模型、编译、JVM 启动、业务验证、证据整理拆分；纯模型推理耗时无法分离时明确使用角色总耗时。比较同一输入的冷/热路径，不把不同场景时间直接相减。

暂不给整项目完成日期。后续先固定 V2-D1 切片和实际依赖，再估算受控兑换、企业交付及必要工程改动。新增检查只为验证具体变化或解决已观察风险，不以完善架构为由增加通用平台建设。
