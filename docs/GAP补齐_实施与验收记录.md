## 2 A 批：来源、状态与开发入口

可观察结果：应用方选择 MOA/Deep 模板时能理解用途和开放范围，创建后得到空业务工程，业务目标可以带入 Coding；应用详情显示创建时固定的发行版本。各页显示真实保存版本的阶段状态，平台诊断显示只读入口。

实现：`workbench-server/journey.ts` 从发行提交生成元信息，从现有报告、编码任务、运行和导出生成状态。前端 `journey.js` 共用展示来源、模型说明与状态；平台工程内维护入口沿横向导航，侧栏保留模板切换与开发 Skill/工程活动入口。MOA 预演控制移到图上方；Deep 工具缺省上限不再显示“未声明 次”。

## 3 B 批：可配置约束、开放范围与模板发行

可观察结果：应用方在能力详情里编辑操作确认、完成依据、调用上限和前置条件说明，编辑 Agent/接线草稿并查看移除影响。配置页默认聚焦一个分区，可显式展开全部。平台方维护开放类型；发行前必须完成当前保存提交的真实结构检查，发行页提供历史、文件变化与应用方创建预览。

服务端变化：

- `ProjectStore.publish` 强制读取当前 head 的最新结构报告；缺失、失败、过期均拒绝。发行记录绑定 `checkId`，现有数据库新增可空列，历史发行不伪造报告。
- 新的有限装配契约由固定来源模板控制 Skill/Agent/接管/接线草稿/可写路径，应用文件不能改变自己的授权范围；交易写操作的确认下限在直接保存和发行边界检查。
- 能力来源比较当前保存资产与创建时固定模板，区分模板提供、应用新增和应用覆盖。工程活动增加真实发行记录。
- 为避免读取大模板时重复运行大量 Git 命令，固定提交快照使用最多 64 项/总文本 16 MB 的内存缓存；调用者取得副本，每次仍核对提交归属。不是构建复用机制；不复用旧业务验收。

测试迁移：已有模板夹具改为 `checkedRelease`，实际运行结构检查后再发行；权限、版本、失败及业务断言保留。API/PC 用例显式经过新增检查入口；长表单测试通过可见“展开全部配置”进入原多区流程。真实 E2E 脚本的发行准备也同步增加检查，本批只做类型核验，未运行这些付费模型脚本。

新增测试：`release-contract.test.ts` 覆盖无/失败/过期报告、固定确认下限、模板能力关闭以及快照副本隔离；`pc-release-assembly.test.ts` 覆盖操作规则保存、删除后失效引用保留且检查失败、检查→发行→历史→预览及开放开关不会改写历史版本。

## 6 模型与环境批（2026-10-26）

本批失败用例发现导出清单仍硬编码 deepseek-flash，已修复。包格式 v3 固定原运行实际模型/公开配置，启动脚本和配置样例的默认值来自该记录，仍允许目标环境覆盖；包含无秘密的工程引用，不复制私有目录。历史未记录模型标为 not-recorded。格式变更形成新包，旧包不重写；启动脚本对默认字符串采用 shell 引用。
