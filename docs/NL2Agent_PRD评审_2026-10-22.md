## 1 结论

**作为方案讨论稿，当前文档合格，可以支持 M0 技术验证；作为可冻结并直接交给自动开发流程的完整 P0 PRD，暂不建议通过。** 需要补齐目标用户与价值衡量，并关闭候选测试入口等具体契约缺口。

文档已经明确平台向用户提供开发 Agent 和测试 Agent，交付真实运行的业务 Agent、Skill、Rail、Tool；受限生成、独立执行器、平台验收和可复用企业 Mock 均已纳入范围。分阶段实施没有将这些能力排除出产品范围。这些方向应保留。

最强部分是工程约束和验收追溯：固定候选与版本绑定、真实外部证据、不可自行降低验收标准、审批与幂等、失败分类均有明确要求。最弱部分是产品问题和成功指标：尚不能用文档回答首要服务谁、相较当前方法改善多少，以及何种效果代表平台值得继续投入。

本结论属于文档评审，不是实现、SDK 兼容性或运行安全的验证结果。Skill 提供评审框架，具体合格性判断由本次阅读和交叉核对形成；未运行自动生成 PRD 的质量基准测试。

## 4 需要关闭的具体问题

以下“高／中”表示评审优先级，不等同于需求文档的 P0/P1 版本范围。所有修改均为建议，尚未应用到原文档。

### RV-01【高】候选验收与已发布调用入口没有闭合

**证据：** 需求文档 L239–245 要求先验收再发布，L294、L302 要求执行器部署固定候选；Mock 规格 L122、L133 规定调用入口解析已发布且就绪的版本，但 L143 又要求发布前从模拟 App 入口或同契约客户端执行测试；交互设计 L653 也只允许打开已发布 Agent 的 App。

**影响：** 首次版本可能没有可调用的已发布实例；已有版本时，测试可能命中旧版本，而报告却关联新候选。当前文档没有说明如何在同样的身份、审批、去重规则下调用未发布候选。

**建议与关闭条件：** 定义受执行器控制的候选测试部署和绑定方式，例如绑定 `candidateId`、部署标识、环境及制品摘要。普通 App 继续使用发布入口；测试路由沿用业务调用契约和控制逻辑，但指向固定候选。增加“无任何已发布版本时测试首个候选”和“现行为 v1、测试 v2 候选实际命中 v2”的验收，不能用提前切换正式入口解决。P0-B 端到端验收前关闭。

### RV-02【高】首要用户、当前问题与人工责任未明确

**证据：** 需求文档 L11–19 主要描述建设方案，L47–53 列出业务使用者、Agent 开发者和维护者；L59、L286、L300 分别要求用户确认需求、审阅变更和确认测试集，但没有规定首要使用者应具备什么能力。

**影响：** 如果首要用户是非技术业务人员，审核 Java 变更和测试断言可能超出其能力；如果首要用户是企业 Agent 开发者，默认流程、诊断深度和价值目标会不同。

**建议与关闭条件：** 增加一页产品问题说明，明确首要用户、当前完成同一任务的方法、主要困难、最希望改善的结果，以及需求确认、代码审阅、测试基线确认各由谁承担。现有三类角色可以保留；无调研证据的描述标记“假设”，不补造访谈或数据。整体产品基线冻结前明确；不阻塞已有方向下的 M0 技术核验。

### RV-03【高】缺少衡量自动开发价值的成功指标

**证据：** 需求第 10–12 章包含演示、40 个 AC 和里程碑；NFR-05 定义普通保存／列表请求性能，但没有自动开发效率、成功率、人工介入和成本的衡量口径。

**影响：** 即使演示通过，也无法判断平台是否降低了开发成本，或是否需要大量人工修复才能交付。

**建议与关闭条件：** 先固定代表性任务集和统计口径，再测现状、定目标。建议指标见第 5 节；目标值、样本数和观察窗口均待确认，不以本报告建议冒充已批准承诺。P0 可以验证技术可行性，但完整交付结论应同时说明价值验证结果或尚未验证的范围。

### RV-04【高】生成阶段限制与业务运行阶段限制的验收范围需分清

**证据：** 需求 L286–296、AC-23 重点验证生成／构建越界；L391 已要求服务端强制执行动作策略。Mock L40–42、L135 也要求可信身份及受控写入，但没有明确用生成后的执行文件、Java 扩展或子进程验证绕开正常 Tool 调用路径的情况。

**影响：** 只验证开发 Agent 的权限，不能证明交付后的业务代码也遵守审批、凭据与网络规则。这里是验收覆盖缺口，不是已经发现实现存在绕过漏洞。

**建议与关闭条件：** 明确运行中的生成代码适用哪些限制、由谁执行，以及如何取得业务凭据；审批应覆盖具有相应副作用的实际调用路径。加入负向用例：未确认时，生成代码尝试直接 HTTP 调用或经执行文件写入 Mock 业务服务，仍被阻止且写入证据为零。若某类执行路径无法约束，应保持该路径不可用并列出缺口。开放对应可执行生成能力前关闭。

### RV-05【中】余额不足用例缺少可复现的数据前置条件

**证据：** Mock L71–72 的初始余额为 10000 元和 5000 元；L84 的单笔 Rail 上限为 2000 元；L160 要求覆盖余额不足；L162 要求独立用例从固定状态开始。

**影响：** 在当前默认种子上直接发起单笔申购，满足 Rail 限额的金额不会触发余额不足；大于余额的请求会先被限额阻止。测试设计目前没有指定低余额种子或前置扣款步骤。

**建议与关闭条件：** 增加版本化的低余额用例数据，例如余额 50000 分、申购 100000 分、有效产品及正常确认。预期必须区分业务接口返回 `INSUFFICIENT_BALANCE` 与 Rail 提前拒绝，并核验余额、订单、持仓均未改变。金额是本报告的示例建议，未经确认不是新基线。P0-C 对应用例执行前关闭。

### RV-06【中】P0-B 的阶段验收集合不确定

**证据：** 需求 L91 使用“完成相关新增 AC”，L618 使用“读场景验收通过”；AC-22 同时包含四类生成产物，完整覆盖属于 P0-C，AC-38 等也组合多个条件。

**影响：** 不同实现者会对 P0-B 应通过哪些完整或部分场景作出不同解释；仅把 AC-22 标记通过可能夸大当前阶段能力。

**建议与关闭条件：** 建立阶段—需求—用例映射；组合用例拆成可独立判定的子项，并给 P0-B 明确必测集合、依赖和排除项。保留完整 P0 四类生成要求；不以阶段划分降低整体目标。P0-B 任务拆分前关闭。

### RV-07【中】受限生成的首个可执行能力边界待冻结

**证据：** FR-018 描述允许模板、依赖、命令、网络与预算，M0 要核验生成路径；目前没有首个 GenerationProfile 的具体允许内容与不支持输入列表。

**影响：** 自动开发 Agent 仍需要自行判断支持哪些 OpenAPI 特性、Rail hook、执行文件与依赖，需求中的“受支持”“允许”还不足以构成执行输入。

**建议与关闭条件：** M0 产出最小能力矩阵和策略清单，固定 SDK／模板、接口契约子集、认证方式、Rail hook、命令、网络目的地以及预算默认值和上限。超范围输入须有统一拒绝或待扩展结果。实现细节可放配套设计文件，PRD 引用版本与验收条件；不必在技术核验前猜出全部数值。

### RV-08【中】待核验项和风险没有统一关闭机制

**证据：** 需求 L65、L479、L613、L621–623 和交互 L617–619 分散列出 OpenCode、SDK、Skill、确认续接、取消和隔离的核验任务；有里程碑，但没有逐项责任人、结论和不成立时的处理记录。

**影响：** 拟议方案可能被后续开发误读为已验证能力；技术风险之外，用户是否能完成审阅、是否降低人工投入也可能一直未验证。

**建议与关闭条件：** 增加未决问题／风险表，包含编号、事实或假设、影响范围、责任人、最晚关闭阶段、验证方法、证据、决策和状态。责任人未知时写待确认；用阶段节点表达时限，不虚构日历承诺。M0 结束时记录技术核验结果及对范围的影响。

## 5 建议的价值指标口径

以下是评审建议，不是已批准目标。先固定受限生成能力范围、代表性任务集、模型配置、预算和测量规则；同一任务的修复次数与人工介入均保留。

| 指标 | 建议口径 | 待确定内容 |
| --- | --- | --- |
| 交付成功率 | 预算内通过独立验收的任务数／固定任务集中已启动任务数；分别披露失败、取消、环境阻塞和未验证数量，不静默剔除 | 任务集、重复次数、目标比例 |
| 达到首次验收通过的时间 | 从启动到首个通过候选的实际耗时，包含构建、测试、修复及等待；成功任务统计分位数，同时报告超时与失败比例 | 与人工流程对照的基线、观察窗口和目标 |
| 人工介入 | 分开记录预期的需求／审批确认，以及非预期的手工改代码、改测试和修复环境；统计次数与人工耗时 | 哪些介入属于产品正常流程、可接受水平 |
| 每个合格交付的资源成本 | 固定任务集全部执行与修复成本／合格交付数；零交付时报告零成功及总消耗，不产生虚假均值 | 可获取的模型费用、计算资源口径和预算 |
| 硬性约束 | 未授权业务效果、验收基线被擅自降低、无证据却通过等按逐项断言判定，不用平均模型评分抵消 | 按已有强制规则补齐负向用例与证据 |
