# 一致性诊断与关联修订

入口为“测试 → 一致性检查”。OpenCode负责判断业务范围、应用层System Prompt、挂载业务Skill和操作定义是否一致；服务端只校验来源、版本、结构和执行边界，不用关键词规则替代语义判断。

1. 保存工程后发起检查。助手在固定提交的隔离副本中加载角色开发Skill，实际读取 application.json、instructions.md及全部业务Skill；结合操作定义和相关实现给出 `clear`、`conflict` 或 `needs-clarification`。
2. 页面列出冲突来源、业务影响、关联修订建议及原助手证据。诊断任务只允许写结构化报告，不修改源文件。该报告写入原Coding记录后清理任务副本，不应用到工程。
3. 明确业务取舍后交给Coding生成关联修订；需要澄清时必须提供修订意图。沿用原任务问答、取消、差异审阅、拒绝及过期保护。应用生成新的Git提交，不自动宣布问题解决。
4. 对新版本重新诊断，再运行受影响的业务用例。语义一致不等于业务通过，也不等于企业发布完成。

报告绑定原任务、引擎、源码head、公开模型配置、输入摘要与来源路径。只有实际OpenCode引擎才显示真实OpenCode分析；契约引擎记录显式标记，不能作为真实模型验证。

**复用规则**：输入摘要包含固定工程中除 `tests/`、`runtime-tests/`、`README.md`、`.gitignore` 外的所有文件，按路径排序计算。只改测试或上述文档时可复用同摘要的诊断，页面明确展示原源码head与复用原因，不伪造新分析。其他文件变化均需重新分析。业务测试报告仍必须绑定当前完整源码版本；复用语义分析不复用旧业务测试。

没有诊断记录时允许普通快速调试，但不显示已验证。已有冲突、业务歧义或修订后未复核时，相关定义版本的新运行、消息、确认和续办被阻断；状态读取、回放、原回执核对、明确拒绝和暂不切换仍可请求。执行器自身的授权/状态校验继续生效，诊断不能覆盖它。新版本修复不会解除旧运行所绑定冲突定义的限制，也不会迁移在途任务。

工程中自行填写的 `tests/.workbench-consistency.json` 不是证据。发起诊断前仅从隔离任务副本移除旧文件，要求本轮真实产出；服务端核对实际读取证据、输入摘要与来源路径。失败、取消、无效输出或诊断时擅改源文件不会形成有效结论。诊断和修订共用既有Coding任务保留上限，不新增后台重放或工作流服务。

固定候选的业务证据及企业交接登记见[交付流程](验证候选与企业交接登记.md)。本文描述静态诊断与关联修订，不把契约测试成功或助手摘要当作业务行为证明。

输出兼容规则：助手可能在JSON中增加说明字段。工作台保留本轮原始JSON及其SHA，只提取并严格校验inputDigest、verdict、issues的来源/描述/影响/建议；附加字段不授予权限、不改变结论。缺少核心字段、错误摘要、非法来源、无效结论或超过128000字符仍拒绝。页面可查看原始附加说明，不因说明字段丢弃合法诊断。

阻塞范围只包括真实互斥指令、业务去向矛盾、授权/完成依据违反固定约束，以及实质改变业务主体/结果而不能按已有默认规则确定的取舍。定义可互补，框架提供某工具不代表应用必须使用，不要求每份Skill重复所有程序保护。可选文案、展示格式、未穷尽异常细节及未执行业务测试只作附加建议，不能阻断快速Demo开发；缺少订单号等运行时输入交给原任务澄清。
