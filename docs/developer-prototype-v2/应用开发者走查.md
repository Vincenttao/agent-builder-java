# 应用开发者流程走查与修正

日期：2026-10-24。批次：DEMO-01；层级：静态 UI 与产品设计。目标是让全新应用开发者独立完成“MOA 模板 → 需求 → 开发 → 调试 → 交付预演”。不启动第二、三阶段的真实前后端开发。

## 走查结论

上次修改只分开了模板和业务名称，仍把业务用户的兑换过程当成应用开发过程。新应用开发者应获得可用的 MOA 开发起点；i豆来自他提出的应用需求。开发者的工作对象是需求、接口契约、规则、代码和测试。选择礼品、确认兑换是调试时模拟业务用户的行为。

以独立浏览器上下文访问 `http://127.0.0.1:8768/`，实际点击、填表并检查页面；同时保留独立自动化检查。原始走查基于提交 `6e3b871`，不只是静态代码推断。

| 原页面实际行为 | 为什么有问题 | 本批修正 |
| --- | --- | --- |
| 新用户模板页侧栏已出现“i豆服务助手” | 创建应用前就带入业务实例 | 没有预建应用，模板目录只有 MOA；创建后才显示应用导航 |
| 创建“员工福利助手”后没有 Agent 输入框，业务页只提示另建示例 | 开发者无法根据自己的目标继续开发 | 立即提供需求输入，形成可审阅方案，应用到当前工程 |
| “填入 i豆示例”覆盖应用名称与业务起点 | 模板实例化与业务实现混在创建器内 | 删除业务示例选择器；i豆方案由开发需求触发，保留名称与目标 |

| 增加资格校验要求先切平台角色发行模板、重新创建 | 新应用开发者无法独立完成工作 | 默认提供已可用 MOA 1.3.0 示例模板；平台维护单独演示，发行不覆盖已有应用 |
| 更换调试礼品增加应用修订、使交付检查过期 | 测试输入被当成代码配置 | 测试输入单独保存；更换礼品仅使待确认交易失效，不改变应用或候选 |

## 修正后实际走过的路径

1. 全新入口只有 MOA 卡片；以“员工福利助手”创建应用，目标为 i豆查询、目录、确认兑换与结果核对。
2. 从 Coding Agent 输入框发送业务目标，审阅预设方案与文件内容，应用到同一工程。
3. 查看余额、目录、兑换与回执契约、确认策略，绑定本地 Mock。查看配置代码，把模型选项改为“轻量调试模型”并保存。
4. 模拟用户查询成功；改用嵌套接口返回，保留映射失败。通过 Agent 查看并应用修复，再查询成功。
5. 模拟用户请求兑换；待确认时改选礼品，确认失效且修订保持 r5。重新发起并确认，生成一笔本地订单，余额为 930。
6. 打开 Trace，查看分步详情。回放只读，不增加订单。
7. 运行示例检查，固定 `candidate-demo-r5`，预演企业交接并下载设计 JSON。全程未切换平台角色。

## 检查与证据边界

- 新旅程检查先在旧页面因入口带入 i豆失败；红灯截图位于本批 `red/`。首次运行新页面时，测试在当前工作区查找“创建应用”超时；应先进入“我的应用”，修正导航后通过。该失败截图位于 `journey/failure.png`，未删除。
- [最终旅程结果](../../test-results/prototype-v2-app-journey/final-journey/result.json)：4 组通过，覆盖新用户入口、同工程方案、连接门槛、测试输入分离、旧记录兼容、旧模板开放范围、非 i豆需求及手机布局。
- [最终交互回归](../../test-results/prototype-v2-app-journey/final-regression/result.json)：7 组通过，保留代码冲突保护、映射故障、拒绝零写入、超时核对不重复写入、只读回放、候选固定与过期、下载标识、刷新及重置隔离、输入转义。包括桌面 1440/1280、手机 390 宽度；零外部 HTTP 请求、零页面脚本异常。
- 原 `verify-template.cjs` 中业务示例选择器的用例被新旅程替代，保留兼容执行入口。既有回归只调整应用创建与可用模板的步骤；未放宽业务硬性断言。新应用继承平台发行的新版本仍有检查。
- 源码语法、单文件构建一致性、修改文档链接和 diff 检查属于本批交付检查。未运行 Java、模型、Docker、真实 OpenCode 或企业 CI，不计 V2-AC 验收。

本批截图、下载清单与检查结果合计约 6.5 MiB。证据使用固定目录，保留失败与修正后的结果；不复制 SDK、不创建运行容器、不覆盖前两批证据。临时隔离浏览器在走查结束后关闭，本地静态预览服务继续可用。可编辑源文件与打开方式见 [Demo 说明](README.md)。
