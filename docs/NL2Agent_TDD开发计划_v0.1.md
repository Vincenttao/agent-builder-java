## 1 TDD 执行规则

本项目采用测试驱动开发。每个行为从已确认 FR／AC／TC 出发，先写可执行测试并确认它因缺少目标行为而失败，再写最小实现，最后在测试保持通过时重构。依赖没安装、测试未被发现或语法错误不算有效红灯。

TDD 适用于业务规则、状态转换、协议、并发与恢复等有明确行为的实现。纯文案、样式或低影响配置不要求为了形式补一条镜像测试，但相关用户流程仍受 E2E 验收约束。

| 步骤 | 开发动作 | 形成的证据 |
| --- | --- | --- |
| 1 选行为 | 选择一个可独立判断的 AC 子项及失败分支；固定输入和观察结果 | 需求编号、测试名称、前置数据 |
| 2 红灯 | 在正确装配的测试环境中运行，确认失败原因是待实现行为 | 测试命令、退出码、断言失败摘要 |
| 3 绿灯 | 实现满足该行为的最小代码，不扩大功能范围 | 同一测试及关联回归通过 |
| 4 重构 | 调整边界、命名、重复代码；保持公开行为 | 类型检查、测试和代码审阅 |
| 5 集成 | 替换为真实数据库／Runner／SDK 适配器验证契约 | 相应集成与真实运行记录 |
| 6 验收 | 固定平台版本或候选，运行阶段必测集合 | 完整报告、制品与外部证据 |

缺陷修复先补能复现缺陷的失败测试。不能通过删除测试、降低期望、无条件重试或只保留最后一次成功消除失败。测试隔离依赖独立数据与进程管理，不声称已实现执行沙箱。

## 2 两种开发循环

### 2.1 开发 agent-builder 平台自身

平台开发人员或工程助手负责平台代码和测试；以本仓库验收基线为事实来源。优先用假时钟和接口替身测试规则，再用真实数据库和真实外部适配验证。测试目录、数据准备和 CI 分组从第一批代码建立，不等 UI 完成后再补。

### 2.2 平台为用户自动开发业务 Agent

平台先确认需求，测试 Agent 据需求准备业务 TestPlan，开发 Agent 为生成工程编写并运行单测，然后实现、构建候选。独立执行器使用固定候选和已确认断言执行；平台读取真实接口／状态并作出裁定。

自动开发日志区分测试、实现、构建与候选验收。开发角色单测允许纠错并保留差异，但不得降低已确认的独立验收基线或削弱既有业务断言。代码缺陷在组件层建立红绿，Skill/提示问题在内容或行为层验证；复用已验证组件不人为制造红灯，不要求所有产物先出现指定 Java 错误。测试基线在业务验收前固定，稳定方案无需重新调用测试 Agent。模板物化、样例复用与真实模型生成分别标识。

## 3 测试分层与目录

| 测试层 | 规划位置 | 工具与环境 | 必查行为 |
| --- | --- | --- | --- |
| 领域单测 | 模块内 `*.test.ts` | Vitest、假时钟、内存 Ports | 状态机、策略、摘要规范化、审批、预算、结果分类 |
| API 契约 | `tests/contract` | Fastify inject、固定 Schema | 非法输入、身份与目标绑定、409、错误结构、幂等与分页／事件序号 |
| 数据集成 | `tests/integration` | 真实临时 PostgreSQL | 事务、唯一键、并发请求、版本切换、恢复与租约 |
| Java 适配 | `java/runtime-bridge` 和模板测试 | 与 SDK 相容的 JUnit／Maven | 真正装配、Rail 顺序与触发、Skill 路径、续接与取消 |
| 引擎与进程 | `tests/live/adapters` | 固定 OpenCode、Runner、真实子进程 | 会话映射、事件、命令模板、退出／超时／进程树停止 |
| 浏览器 E2E | `tests/e2e` | Playwright、真实 Web/API | 问答编辑、冲突、确认、SSE 重连、候选／发布分流、App 身份切换 |
| 阶段验收 | `tests/acceptance` | 固定平台与真实 Java Agent／模型、Mock | 当前阶段全部 AC／TC／NF，证据与版本绑定 |
| 交付评测 | `tests/evaluation` | 固定 EV 任务包、模型、预算与重复计划 | 自动开发到独立验收及演示就绪的完整成功率 |

前端组件测试可使用接口替身，但阶段 E2E 不拦截真实业务请求伪造成功。SDK 协议测试可用确定性模型替身，真实生成／运行验收必须明确切换真实模型；两类报告使用不同标识。

## 4 优先实现的测试接口

Clock、IdGenerator、ModelPort、EnginePort、RunnerPort、JavaRuntimePort、ArtifactStore、MockControlPort、EvidencePort 均通过构造参数或应用装配传入。禁止领域对象在构造中启动服务、连接数据库或读个人环境变量。

测试替身提供明确行为：模型返回缺字段、Runner 返回错误制品、事件乱序／重复、Mock 写成功后断连接、时钟到达动作期限。不得让替身永远返回成功，也不得让被测实现读取测试期望作为业务结果。

测试金额固定为整数分；低余额使用专用种子。并发测试通过屏障同时发起请求，不以“循环调用两次”代替竞争场景。时间推进用假时钟测试规则；真实超时与进程停止另做集成验证。

### TD-12 分阶段红—绿门禁

TD-12 不作为单一交付批次。每个增量均先写可观察的失败测试，分别验证生成输入、策略拒绝、构建产物、真实装载和业务行为；只有当前增量全部通过，才开放对应生成类型。

| 增量 | 红测试先覆盖 | 绿实现边界 | 禁止提前宣称 |
| --- | --- | --- | --- |
| TD-12A Skill 扩展 | 未登记 Tool 引用、格式不合法、模型未加载 Skill、返回事实与 Mock 不一致 | 复用固定 Skill 执行模板，绑定实际候选 Tool 与摘要 | 不宣称任意 Skill 脚本执行或金融接口已接通 |
| TD-12B Rail 定义生成 | 参数越界／未知字段拒绝、阈值边界、hook 未触发、跨会话污染 | 仅接受登记的 Rail 模板与 JSON Schema；固定 Java 适配器装配真实 SDK hook | 不开放模型生成任意 Rail Java 源码 |
| TD-12C Agent 工程生成 | SDK 类型／版本错误、AgentSpec 与源码不一致、装配清单缺件、失败后假成功 | 生成可审阅的工程入口与映射，复用 SDK DeepAgent Loop | 仅保存 AgentSpec 不算 Agent 工程生成通过 |
| TD-12D 写组件组合 | 未确认／拒绝／跨身份／重复／超时后账本调用断言 | 在登记的 Mock 写接口上生成 Tool、Skill 和确认参数；由平台核对外部状态 | 不连接真实企业写接口，不允许模型改确认规则 |

单次工具调用上限模板的历史验证见 TDD-021。后续能力按 RP-04/05 的实际缺口推进；参数化模板的通过不代表任意 Rail 源码生成通过。

## 6 关键行为测试示例

以下为测试意图示例，fixture 名称和代码需在实施时创建，不能视为已经存在或已运行的测试。

```ts
it('AC-41b: 候选请求不能落到现行发布版本', async () => {
  const h = await createRoutingHarness();
  await h.publish({ agentId: 'a1', version: 'v1', digest: 'digest-v1' });
  const candidate = await h.createCandidate({ digest: 'digest-v2' });
  const deployment = await h.startTestDeployment(candidate);

  const result = await h.sendTestMessage(deployment, '查询余额');

  expect(result.target.artifactDigest).toBe('digest-v2');
  expect(h.runtime.invocations.at(-1)?.artifactDigest).toBe('digest-v2');
  expect(await h.currentRelease('a1')).toBe('v1');
});
```

该契约测试可以用 RuntimePort 替身证明路由规则；集成版本必须换成两个实际 JVM，并使它们返回可区分结果、核验真实装载摘要，不能只验证 DTO 中填了 v2。

```ts
it('AC-11: 并发重复批准只产生一个有效动作和一次业务效果', async () => {
  const h = await createApprovalHarnessWithPostgresAndMock();
  const action = await h.preparePendingAction();

  await Promise.all([
    h.approve(action, 'decision-1'),
    h.approve(action, 'decision-1'),
  ]);
  await h.waitForActionTerminal(action.id);

  expect(await h.countEffectiveDecisions(action.id)).toBe(1);
  expect(await h.mock.countBusinessEffects(action.businessKey)).toBe(1);
});
```

另测未确认、拒绝、过期、改参数时下游写调用为零；另测写后超时可能有重复 HTTP 请求，但业务效果仍一次。数据库和 Mock 的记录由测试查询，不能只断言页面文字或模型输出。

## 7 本地检查与正式验收

以[推进计划第 4～5 节](后续推进计划与执行要求.md)的变更矩阵与证据过渡规则为准。GitHub CI 不作为当前本地推进的阻塞条件；重大完整变更在必要检查后本地提交，不自动推送。

现有入口包括 `pnpm typecheck`、`pnpm test:unit`、`pnpm test:contract`、`pnpm test:integration`、`pnpm test:live:adapters`、`pnpm test:e2e`、`pnpm build` 和 `pnpm test:acceptance`，实际参数以 package.json 与脚本为准。定向 Vitest 文件选择优先；lint、contracts:check、eval:delivery 未提供前不作为执行门禁。

普通修改只跑受影响的检查。文档修改不构建；UI 修改不编译 Java；不变组件不重新生成。需要交付部署时构建受影响镜像一次，并批量执行相关检查；切换测试用例不触发重建。纯镜像存储迁移且摘要/配置不变时只做迁移健康检查。

完整 P0 阶段交付仍须覆盖累积必测集合，真实模型要求不能用替身通过替代。平台版本与业务候选版本分别记录；新镜像不自动触发每次开发循环的全量回归，也不自动获得旧证据的通过状态。正式检查器尚未支持的跨版本复用，保持原目标记录及未验证状态；新规则实现并验证后才可纳入阶段汇总。

故障先分类：脚本错误只修脚本并重跑相应用例；环境恢复后重跑受阻检查；实现修复执行影响范围内回归。默认测试重试为 0，诊断复跑保留全部结果。破坏性测试串行并核对恢复，不用固定 sleep 掩盖竞争。

不以测试数量或统一覆盖率证明完成。每批关注实际变化、保护逻辑的有效断言、正确证据绑定和资源退出；完整阶段报告安排在正式交付批次。

## 8 测试清单与报告格式

实施时维护机器可读的 `tests/acceptance/manifest.json`，每条至少记录 `caseId/requirementIds/phase/testFile/evidenceKinds/executionMode`。manifest 必须展开复合 AC 的子项，并区分正常路径与负向分支；当前 42 个父 AC 展开为 56 个平台条目，另外包含 26 个业务条目和 6 个 NF 条目，具体分组以验收基线为准。

校验器检查：引用存在、阶段集合无漏项、同条目所有必需分支均有结果、用例未被 skip、实际制品与报告一致、证据可读取。用例集合里没有测试不能得到“0 失败所以通过”。父 AC 不因某一子项通过而整体通过。

报告保存平台 commit、依赖／模型配置、基线、候选、部署、环境／数据／故障、测试命令、开始结束时间、退出码、断言与证据。开发循环可记录红绿证据摘要；正式验收报告只汇总固定版本，但仍关联历史失败，不覆盖旧记录。

## 9 每个工作包的完成条件

1. 行为和编号可追溯；行为实现/缺陷修复有适当层次的失败复现与通过结果，纯文档或样式不强造红灯。
2. 对本批变化相关的正常/失败分支有测试；涉及副作用才增加相应重复请求和恢复检查，不在每批重跑所有分支。
3. 数据写入、版本／权限／副作用相关行为有真实数据库或外部状态证据。
4. 替身与真实运行结果分开，必要的 SDK／引擎契约已通过；未验证项如实阻塞对应能力。
5. 模块关系符合技术设计，无领域层直接依赖 HTTP／数据库／引擎；生成代码不进入管理进程。
6. 文档、配置和阶段 manifest 同步；没有虚假通过、凭据进入日志／导出或降低验收标准。

7. 生成/构建相关变更记录模型调用、编译与打包次数、临时文件退出情况；资源复用改造需证明重复运行不线性复制大文件。
