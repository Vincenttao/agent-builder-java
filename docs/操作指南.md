## 选择使用方式

| 目标 | 建议方式 | 需要准备 |
| --- | --- | --- |
| 本机体验、团队演示 | Docker Compose 完整部署 | Docker、Node.js、模型密钥 |
| 修改 TS／React 代码 | PostgreSQL 容器 + 宿主机服务 | 再安装 pnpm；执行 Agent 还需 JDK、Maven、Git |
| 查看项目介绍 | 直接打开 [项目汇报 HTML](项目汇报.html) | 浏览器；不需要运行后端 |
| 查看已有验证结果 | [TDD-016](implementation/TDD-016.md)、[TDD-017](implementation/TDD-017.md) | 无需重新调用模型 |

本期使用可信本地模式（trusted-local）。生成内容限定为设备只读 Tool／Skill；Docker 用于统一部署，尚未提供独立任务沙箱或生产多租户隔离。这里的“发布”指切换本地演示入口。

### 先区分五个对象

| 对象 | 含义 | 后续修改的影响 |
| --- | --- | --- |
| 草稿 Draft | 可编辑需求，包含修订号 | 修改后形成新修订 |
| 验收基线 Baseline | 已确认的需求、场景与预期 | 绑定需求修订和模板，不跟随编辑变化 |
| 测试快照 Snapshot | 固定需求与 Agent 装配定义 | 后续编辑草稿不会修改它 |
| 候选 Candidate | 待测试的固定运行制品，可来自模板或自动生成 | 新代码需要登记新候选 |
| 发布版本 ReleaseVersion | 已通过验收和发布冒烟的演示目标 | 新业务会话使用现行版本，旧会话保留原目标 |

## 安装与配置

### 环境要求

| 项目 | 当前项目要求 |
| --- | --- |
| 操作系统 | Windows + Docker Desktop Linux 容器可使用；Compose 镜像为 Linux 镜像 |
| Node.js | `package.json` 要求 ≥ 22.12；推荐 24，Docker 镜像固定 24 系列 |
| Docker | 支持 Compose v2、BuildKit、`up --wait` 的安装 |
| pnpm | 宿主机开发使用 10.32.1；纯 Docker 启动不要求宿主机安装 |
| Java 工具链 | 纯 Docker 已内置；宿主机执行需要 JDK 21、Maven 3.9、Git |
| 模型 | 项目默认请求 DeepSeek `deepseek-v4-flash` |
| 网络 | 首次构建需获取镜像、npm 依赖、固定 Git 提交和 Maven 依赖；真实运行需连接模型服务 |

尚未完成最低硬件配置和性能基准测试；不要将开发机配置当作产品容量承诺。

### 配置步骤

```powershell
node --version
docker version
docker compose version
node scripts/init-local.mjs
```

编辑生成的 `.env.local`，填入模型密钥，并保留生成的本地访问令牌。初始化脚本只补缺失键，不修复已有占位符，也不会自动轮换已有密码。

| 配置项 | 用途 | 操作建议 |
| --- | --- | --- |
| `DEEPSEEK_API_KEY` | 工程开发与业务 Agent 的模型调用 | 本地填写；勿放入代码、截图或汇报材料 |
| `LOCAL_BOOTSTRAP_TOKEN` | 管理工作台登录 | 使用初始化脚本生成的值 |
| `POSTGRES_PASSWORD`、`MOCK_DB_PASSWORD` | 平台库和 Mock 库密码 | 初始化后保留；有旧数据卷时只改环境文件不会改数据库密码 |
| `DATABASE_URL`、`MOCK_DATABASE_URL` | 宿主机服务访问数据库 | 默认指向 15433；Compose 内部自行使用容器地址 |
| `APP_ORIGIN` | 浏览器来源校验 | 默认 `http://127.0.0.1:8080`，访问地址需一致 |
| `RUNNER_BASE_URL`、`MOCK_BASE_URL` | 宿主机服务间通信 | 默认 8081、8082；Compose 使用服务名 |
| `RUNNER_CONTROL_TOKEN`、`TOOL_PROXY_TOKEN`、`MOCK_CONTROL_TOKEN`、`MOCK_SERVICE_TOKEN` | 服务间认证 | 保持相关服务配置一致 |
| `DEEPSEEK_BASE_URL`、`DEEPSEEK_MODEL` | 模型探测脚本配置 | **不代表完整平台可动态切换模型**，见下文 |

当前工程模型由 `apps/runner/src/engineering/profile.ts` 与 `engine.ts` 固定；业务模型由 `apps/runner/src/runtime/model-profile.ts` 固定。根目录 `opencode.json` 用于相应项目配置与探测，Runner 会生成自己的配置。Compose 仅传入模型密钥。修改 `.env.local` 的模型名称或根配置文件，不能保证工程与业务两条链路一起切换；改模型需要调整这些固定配置并重新验证。

### 构建与健康检查

```powershell
docker compose --env-file .env.local config --quiet
docker compose --env-file .env.local up -d --build --wait
docker compose --env-file .env.local ps --all
Invoke-RestMethod http://127.0.0.1:8080/health/ready
```

期望：四个长期服务健康；`migrate` 以 0 退出。`/health/ready` 只验证该接口覆盖的就绪条件；还需登录工作台查看“运行依赖”，并执行一次业务查询核验模型与完整调用链。

| 服务 | 职责 | 完整 Compose 对宿主机暴露 |
| --- | --- | --- |
| `app` | Web、管理 API、业务入口、验收与发布 | `127.0.0.1:8080` |
| `runner` | OpenCode 工程任务、JVM 部署和制品 | 无；容器网络内 8081 |
| `mock-services` | 模拟业务接口、状态及调用证据 | 无；容器网络内 8082 |
| `postgres` | 平台数据库与独立 Mock 数据库 | 无；容器网络内 5432 |
| `migrate` | 一次性迁移与 Mock 数据库初始化 | 无 |

使用 `http://127.0.0.1:8080` 登录，勿在保持默认 `APP_ORIGIN` 时改用 `localhost` 或局域网 IP。首期只绑定本机地址；多人远程访问需要另行设计身份、访问控制和部署边界。

## 需求与测试版本

1. 使用本地访问令牌进入工作台，点击“新建草稿”。
2. 按下表填写。每个字段填写后需勾选“我已确认此字段”；字段再次编辑会撤销确认。
3. 点击“保存草稿”。未保存的修改或未确认字段会阻止固定版本。
4. 选择“设备状态查询”模板，检查 Agent 指令与最大模型轮次。轮次上限可设置为 1～20。
5. 在“审阅验收基线”展开用例，检查需求、输入、故障条件及预期断言；勾选审阅并点击“确认验收基线”。
6. 点击“固定为测试版本”，记下快照编号。该版本包含当时的装配定义，不受后续草稿编辑影响。

| 字段 | 首次演示建议值 |
| --- | --- |
| Agent 名称 | 设备运维助手 |
| 目标使用者 | 设备运维人员 |
| 业务目标 | 查询设备状态、温度和来源；缺少设备编号时先询问，不猜测数据 |
| 交付内容 | 包含设备编号、状态、温度与来源的设备报告 |
| 调试消息 | 查询 PUMP-001 的状态、温度与来源。 |

“引导填写”目前是表单问题提示，尚未接入自由对话式模型澄清。当前验收基线来自固定场景模板，并不会自动把任意自然语言要求转成完整可执行测试。

### 查看组件并装配

工作台的“组件目录”支持按 Skill、Rail、Tool 筛选；未创建草稿时也可以浏览。当前目录是随平台发布的固定组件清单，不是跨项目组件市场。

1. 保存需求后，在“选择组件与装配”选择能力模板，或勾选“装配维修工单”。
2. 设备查询 Tool 是当前两种组合的基础能力。选择工单时，自动加入工单 Tool 与写入确认 Rail；取消选择会移除两者。执行审计与工具白名单随模板启用。
3. 核对“装配预览”中的 DeepAgent、Tool 和 Rail。组件切换会更新默认指令；手动编写的指令保持原样，需要自行核对是否与能力一致。
4. 审阅对应验收基线，再点击“固定为测试版本”。实际配置随快照保存，已有快照不受后续选择影响；未固定的组件选择不会单独持久化。
5. 如需设备查询 Skill，使用设备只读组合固定版本并启动自动开发。构建完成后刷新可用构建，选择生成任务并登记候选。候选区显示实际绑定的 `equipment-query` Skill，其版本由制品摘要固定。

模板候选没有绑定 Skill；目录中的“需自动开发”不表示已生成可用版本。工单组合暂不支持生成 Skill；三个 Rail 为现有内置实现，当前页面按受支持的能力组合启用，不提供任意插件组合或 Rail 代码生成。

### 调试固定模板

在快照卡片的“调试消息”输入完整问题，点击“运行此版本”。观察状态和回答，展开“查看执行轨迹”“查看外部调用证据”，核对实际工具调用及 Mock 结果。需要停止时点击“取消运行”。刷新页面后重新选择草稿，可查运行历史。

**这一入口调试快照的模板装配。** 审阅自动生成代码时，请使用下节的“独立预览”或指定候选的自动验收，以保证执行的是生成 JAR。

## 自动开发与候选验收

前置条件：设备只读快照、同一需求修订的已确认只读基线、运行依赖就绪和有效模型密钥。工单模板当前不能启动此 Tool／Skill 自动开发路径。

### 启动双角色开发

1. 在快照内“自动开发 Tool 与 Skill”点击“启动双角色开发”。
2. 观察测试 Agent、开发 Agent 的会话状态及“开发与测试执行记录”。当前流程先固定测试方案，再执行开发；两个角色不是并行修改同一工程。
3. 测试 Agent 根据已确认基线准备方案。开发 Agent 编写单测，在初始实现上取得真实失败，再编写实现并通过单测；平台再执行独立契约检查和构建。
4. 状态为“构建完成”后，点击文件按钮审阅 Java Tool、Skill、测试与方案；通过“查看执行证据”检查命令、退出码和输出。

单次工程任务最多 900 秒，这是执行预算，不是成功交付时限。关闭页面不会停止任务；需要停止时点击“取消开发任务”。失败或“待核对”时先查看诊断和记录，不把重新点击等同于恢复旧进程。

当前生成配置为 `equipment-java@2`，限制依赖、文件路径、导入、操作与命令。Tool／Skill 可生成；业务 Agent 和 Rail 仍按预置模板装配。受限工具接口有助于约束生成，但尚不构成操作系统级沙箱。

### 登记固定候选

1. 点击“刷新可用构建”。
2. 在“候选来源”选择刚完成的“生成 Tool 与 Skill · 任务编号”。保留“模板装配”会测试模板，而非新代码。
3. 点击“登记固定候选”，确认显示“来源：自动生成 Tool 与 Skill”。
4. 展开“固定制品与装配摘要”，检查候选 ID、开发任务和制品摘要。登记后内容不可直接替换。

### 手动预览候选

点击“启动独立预览”，等待“就绪”；选择模拟身份 U1001 或 U1002，点击“进入候选预览”，发送完整设备问题。查看“演示详情与证据”中的候选与制品绑定。

预览使用独立 JVM 与 Mock 环境，不要求先发布。部署有效期最长一小时，同时最多四个活动测试部署；以页面显示的到期时间为准。关闭页面不会立即停止部署。结束预览时先完成或取消活动请求，再点击“停止测试部署”；历史记录仍保留。

### 执行独立验收

1. 确认“自动验收目标”是所需候选。刚登记的候选通常自动选中；刷新页面后务必再次核对，不要误留“当前模板装配”。
2. 检查“使用验收基线”，点击“运行验收用例”。
3. 平台逐用例创建独立数据环境与测试部署，通过真实 `/test-api` HTTP 入口执行，再收集 Run、工具事件和 Mock 外部事实。测试结束停止相应部署。
4. 展开各项结果和“查看证据”。检查预期与实际值，以及“验收版本与摘要”中的候选、测试计划和实际 JAR 绑定。

| 设备只读必测场景 | 主要判断 |
| --- | --- |
| 正常查询 | 返回设备事实、实际工具调用和 Mock 记录一致 |
| 缺少设备编号 | 不执行无依据查询，要求补充信息 |
| 工具超时 | 明确报告无法完成，不伪造成功数据 |

| 报告状态 | 含义 | 下一步 |
| --- | --- | --- |
| 通过 | 固定基线内所有必需断言满足 | 审阅后发布 |
| 未通过 | 已执行，并有断言失败 | 查看事实证据；符合条件时按失败证据修复 |
| 阻塞 | 依赖或环境不满足执行条件 | 修复环境，再发起新验收 |
| 未验证 | 未实现、未完成或证据不足，含不符合真实模型模式的结果 | 补齐验证；不能用来发布 |

确定性断言决定当前门禁。通用模型语义评分尚未实现，报告通过不覆盖任意额外业务要求，也不等于 agent-builder 平台的完整 PRD 通过。

## 发布与模拟企业 App

### 发布

1. 在该快照“验证记录”中选择通过的真实模型验收报告。
2. 到“演示发布”，勾选“我已审阅验收报告，同意切换演示入口”，点击“发布此验证版本”。
3. 等待“准备部署 → 只读冒烟中 → 发布成功”。平台重新检查绑定和依赖，再使用已验收的同一 JAR 准备运行实例。
4. 展开“发布历史”查看只读冒烟证据。发布失败时原入口保留；清理待核对状态也会显示在页面。

### 调用已发布版本

1. 回到草稿区域“模拟企业 App · 虚构业务数据”。
2. 选择 U1001 或 U1002，点击“进入模拟 App”。
3. 输入 `查询 PUMP-001 的状态、温度与来源。`，点击“发送业务请求”。
4. 查看回答和“演示详情与证据”。核对 requestId、runId、agentVersion、actorId 和外部调用。
5. 同一浏览器标签页刷新后，重新登录管理工作台、选择草稿及相同业务身份，再进入模拟 App，可恢复已记录请求。凭据由服务重新发放，浏览器只保留请求／会话定位信息。

新会话固定当时的现行版本；已有会话保持原版本。发布更新后点击“新建业务会话”才能使用新目标。当前每条消息必须包含完整问题，尚未提供跨消息的 SDK 对话记忆。出现“重试原请求”时应重试原键，避免另建请求误认为同一操作。

### 回滚与重启

在“发布历史”选择历史版本，勾选审阅后点击“回滚到 …”。回滚会重新准备历史制品并进行冒烟，随后切换指针；不会回滚业务账本或删除旧运行记录。依赖变化时历史报告也可能不再适用，需要重新验收。

Runner 重启会停止原 JVM；发布记录持久化不等于进程继续存在。重启后如目标不可用，重新发布仍满足条件的版本，若 Mock／依赖已变更则先重新验收。随后新建业务会话。历史中断请求不自动重放。

## 工单审批演示

工单模板支持调试、八项自动验收和同制品发布。自动生成当前仍限设备只读 Tool／Skill；本节使用固定模板候选。

1. 新建“设备工单助手”，目标填写“查询 PUMP-001，必要时经用户确认创建模拟维修工单”，逐项确认并保存。
2. 选择“设备查询与工单审批”，固定测试版本。可同时审阅该模板的八项验收场景。
3. 发送 `查询 PUMP-001，按查询结果申请模拟维修工单，创建前请让我确认。`
4. 等待“等待确认”，检查设备、描述、优先级及有效期。此时查看外部证据，工单写入应为 0 次。
5. 点击“确认创建模拟工单”，应继续执行并产生一条创建记录；或点击“拒绝并取消运行”，应无创建记录。确认有效期为五分钟。
6. 查询动作绑定及执行轨迹，观察动作参数、用户、Run 与快照的关系。写后超时会按原业务键核对结果，不直接再次写入。

完成模板调试后，可按以下步骤验收并发布：

1. 在“设备查询与工单审批”模板下审阅八项场景，勾选确认并点击“确认验收基线”。
2. 在测试版本中登记“模板装配”候选，核对“自动验收目标”指向该候选。
3. 勾选“允许测试执行器按场景批准模拟工单写入”，点击“运行验收用例”。这项授权仅用于独立 Mock 测试数据。
4. 等待八项执行结束。确认过期场景会实际等待五分钟；不要把等待误认为任务卡死。每项用例使用独立环境，参数变化由平台按固定用例注入，模型和业务请求不能指定该故障。
5. 检查报告：正常查询、缺参追问、只读工具超时、批准与重复确认、拒绝、过期、批准后参数改变、写入后响应超时，均应通过。证据不足或环境失败会阻止发布。
6. 报告通过后审阅并发布。在“模拟企业 App”选择 U1002，发送工单请求。普通业务请求仍需用户手动确认；确认前没有写入，成功后只有一个工单。

参数改变时，原动作变为 `invalidated`（原确认失效），保留批准参数与冲突摘要，并结束该运行。需要改变参数时应重新发起请求、重新确认。写后超时场景通过原幂等键查询已提交工单，不重复写入。

**旧基线升级：** TDD-017 的工单断言版本为 `equipment-workorder-assertions@2`。历史基线与报告保留；旧规则不能启动新验收或发布。若提示 `BASELINE_RULES_CHANGED` 或没有可用基线，重新选择工单模板，审阅并确认八项场景，再对原固定候选发起新验证。无需删除历史记录。只读基线仍为原版本。

本批真实 Docker 证据见 [TDD-017](implementation/TDD-017.md)。八项通过表示该固定工单基线通过，平台完整 PRD 和交付成功率仍需另行验收。

## 失败修复

前置：自动生成候选的完整失败报告；各用例已经结束，存在明确失败断言，且没有阻塞／未验证项。通过报告、模板报告或证据缺失的报告不能进入该修复路径。

1. 在“验证记录”选择目标失败报告，核对候选与基线。
2. 在“自动开发 Tool 与 Skill”点击“按失败证据修复”。
3. 平台复制旧实现、Skill 与旧测试到新目录，保留原报告及固定测试方案。此轮测试角色显示“复用固定方案”。
4. 开发 Agent 先新增回归测试，在未改动的旧代码上取得断言失败；通过后才解锁实现修改。旧测试与新回归测试一起执行。
5. 构建成功后，刷新构建列表，登记**新的**生成候选，再对该候选运行全部三项验收。原报告不能直接验证新代码。
6. 新报告通过后，按常规流程审阅并发布。

每个初始开发任务最多修复三次；每次 900 秒，失败和取消均计入次数。不允许借修复接口修改需求或放宽基线。当前支持设备实现的可复现缺陷，尚不支持任意业务故障分类和无人操作的无限循环。TDD-016 的真实模型修复证据使用预置缺陷作为起点，不表示首轮坏代码也是模型生成。

## 接口接入

当前 UI 已覆盖主要入口；接入脚本时应沿用平台身份和版本绑定。以下路径用于本地联调，不代表稳定的对外生产 API 承诺。

| 入口 | 用途 | 认证 |
| --- | --- | --- |
| `/api/*` | 草稿、基线、工程任务、候选、验收与发布 | 管理 Cookie；写操作要求 Origin 和 CSRF |
| `POST /api/demo-sessions` | 为已发布 Agent 发放模拟业务凭据 | 管理认证；body 为 `agentId`、`actorId` |
| `POST /agent-api/agents/:agentId/messages` | 调用已发布 Agent | 独立 Bearer 业务令牌 |
| `GET /agent-api/requests/:id` | 读取原请求与 Run 状态 | 同一业务身份 |
| `POST /agent-api/requests/:id/cancel` | 取消原请求 | 同一业务身份 |
| `POST /agent-api/requests/:id/actions/:actionId/decision` | 确认或拒绝待办动作 | 同一业务身份、actionHash 和 decisionId |
| `POST /api/test-deployments/:id/sessions` | 发放候选测试凭据 | 管理认证；body 为 `actorId` |
| `/test-api/deployments/:id/messages`、`/requests/:id` | 调用／读取固定候选测试请求 | 与部署和身份绑定的测试 Bearer 令牌 |

发送消息的 JSON 示例：

```json
{
  "clientRequestId": "替换为本次请求的 UUID，重试时保持不变",
  "input": "查询 PUMP-001 的状态、温度与来源。"
}
```

响应包含 requestId、conversationId 及版本／运行信息。后续同一业务会话可携带 conversationId。调用方不能用消息内容指定 actorId、审批状态、任意制品路径或底层业务幂等键。管理令牌不能直接充当业务 Bearer 令牌。完整形状以 [契约类型](../packages/contracts/src/invocations.ts)、[业务路由](../apps/server/src/invocations/routes.ts)和[候选路由](../apps/server/src/candidates/routes.ts)为准。

docker compose --env-file .env.local ps --all
docker compose --env-file .env.local logs --tail 100 app runner mock-services

### 数据保存在哪里

| 内容 | Docker | 宿主机开发 |
| --- | --- | --- |
| 需求、快照、任务、事件、报告、发布记录 | `pg-data` 命名卷中的平台库 | 同一 PostgreSQL 开发实例 |
| Mock 业务数据、调用记录、账本 | 同一 PG 实例中的独立 Mock 库和角色 | `MOCK_DATABASE_URL` 指向的库 |
| 工程目录、固定制品、执行记录 | `runner-data` 命名卷，挂载 `/data` | 默认 `.cache/runner` |
| 本地凭据 | 宿主机 `.env.local` | 同左 |
| 固定验证证据 | 仓库 `docs/implementation/evidence` | 同左 |

备份需要同时保留数据库、Runner 制品和私有配置。仅备份数据库不足以恢复生成 JAR。当前还未完成“全新目录恢复”的正式验收，以下步骤用于保存一致材料，不构成已经验证的灾难恢复方案。

### 保存本地备份

先在页面确认活动任务均已结束。下面的停止操作会短暂停止工作台；不会删除容器卷。

```powershell
$backupDir = Join-Path (Get-Location) ('.cache/backups/' + (Get-Date -Format 'yyyyMMdd-HHmmss'))
New-Item -ItemType Directory -Path $backupDir -Force | Out-Null
docker compose --env-file .env.local stop app runner mock-services

# 在容器内输出文件，避免 PowerShell 重定向改变 SQL 编码
docker compose --env-file .env.local exec -T postgres pg_dump -U builder -d builder -f /tmp/builder-backup.sql
docker compose --env-file .env.local exec -T postgres pg_dump -U builder -d builder_mock -f /tmp/mock-backup.sql
docker compose --env-file .env.local cp postgres:/tmp/builder-backup.sql "$backupDir/builder.sql"
docker compose --env-file .env.local cp postgres:/tmp/mock-backup.sql "$backupDir/mock.sql"
docker compose --env-file .env.local run --rm --no-deps --entrypoint tar --volume "${backupDir}:/backup" runner -czf /backup/runner-data.tgz -C /data .
Copy-Item -LiteralPath .env.local -Destination (Join-Path $backupDir '.env.local')
Get-ChildItem -LiteralPath $backupDir -Force | Select-Object Name, Length

docker compose --env-file .env.local up -d --wait
```

每条命令均应检查是否成功；备份私有配置后勿公开该目录。恢复时还需对应源码、SDK／镜像版本、数据库迁移版本和正确凭据，并按“发布与模拟企业 App”重新准备 JVM。不要将未验证恢复流程用于覆盖唯一数据副本。

## 开发与测试

### 启动宿主机开发模式

完整 Compose 与宿主机服务会争用 8080 等端口。切换前先结束任务并 `down`，保留数据卷。宿主机模式使用 `compose.dev.yaml` 将开发数据库暴露到 15433。

```powershell

node scripts/init-local.mjs
docker compose --env-file .env.local -f compose.yaml -f compose.dev.yaml up -d postgres --wait
pnpm db:migrate
pwsh -File scripts/bootstrap-java.ps1
pnpm build
```

`bootstrap-java.ps1` 使用 Git 获取锁定的 Core／Runtime 提交，安装 Maven 依赖并执行 Bridge 验证。需 JDK 21、Maven 3.9、Git 和 PowerShell 7 可用。只编辑 Web 而不运行 Agent 时可暂不构建 Java，依赖诊断会显示相应运行限制。

然后在三个独立终端、仓库根目录启动服务：

```powershell

```

```powershell
# 终端 2：Runner
node --env-file=.env.local --import tsx apps/runner/src/main.ts
```

```powershell
# 终端 3：平台，提供 pnpm build 生成的 Web 静态文件
pnpm dev
```

打开 `http://127.0.0.1:8080`。修改 TS 后重启对应服务；`pnpm dev` 本身未启用自动重启。要使用 React 热更新，在平台终端启动前设置 `$env:APP_ORIGIN='http://127.0.0.1:5173'`，再在第四终端执行 `pnpm dev:web`，通过 5173 访问。当前 Vite 仅代理 `/api` 和 `/health`，适用于管理页面开发；`/agent-api` 和 `/test-api` 尚未代理，因此完整 App／候选预览演示请回到 8080 的构建版本。退出热更新模式后清除该终端变量：`Remove-Item Env:APP_ORIGIN`，重新 `pnpm build` 并按默认来源启动平台。

## 常见问题

| 现象 | 排查与处理 |
| --- | --- |
| 登录失败 | 从本机 `.env.local` 读取正确 `LOCAL_BOOTSTRAP_TOKEN`；若改过配置，重新 `up -d`。平台重启后管理会话需重新登录 |
| 写请求被拒绝或来源校验失败 | 地址与 `APP_ORIGIN` 必须一致；开发模式 5173 与 Docker 8080 不能混用；刷新登录以获取新 CSRF |
| 草稿能保存，不能运行 | 点击“刷新诊断”；检查模型密钥、Runner／Mock 健康、内部令牌及 Java 制品；查看 `logs --tail 100` |
| 模型显示已配置，但调用失败 | 配置存在不证明额度、网络或模型权限可用；用实际运行诊断或 `model:probe` 定位 |
| 数据库认证失败 | 检查是否已有旧卷、是否只改了环境密码；不要删除唯一数据卷来掩盖密码不一致 |
| 构建停在 Java／npm 下载 | 检查对应依赖仓库的网络访问，重试构建可复用缓存；SDK 提交固定，不应随意升级绕过构建问题 |
| 8080／15433 被占用 | 检查是否同时启动 Docker 与宿主机服务；使用 `Get-NetTCPConnection -LocalPort 8080,15433 -ErrorAction SilentlyContinue` 定位监听，不随意终止其他项目 |
| “固定为测试版本”不可点 | 确认所有字段已填写、勾选确认并保存；不要只改页面而不保存 |
| “启动双角色开发”不可点 | 必须是设备只读基线；检查匹配的修订及未结束的开发任务 |
| 看不到生成候选 | 任务必须“构建完成”；刷新可用构建，主动选择生成任务再登记 |
| 验收报告目标不是刚生成的代码 | 检查“自动验收目标”；模板调试与候选测试是不同入口 |
| “发布此验证版本”不可点 | 需要当前快照的真实模型通过报告与审阅勾选；fixture、未验证或阻塞均不能发布 |
| `PUBLISHED_DEPENDENCY_CHANGED` | Mock／依赖与旧报告绑定不一致；重新验收、发布，再新建业务会话 |
| 重启后发布记录存在但请求阻塞 | Runner 中旧 JVM 已停止；重新准备发布目标，并新建业务会话。原请求不自动重放 |
| 测试部署不能停止 | 先结束或取消活动业务请求，再停止；关闭页面不会停止部署 |
| 修复按钮没有出现 | 只接受生成候选的完整确定性失败报告；阻塞、未验证或缺证据要先处理原因 |
| 生成、验收或写入状态“待核对” | 检查任务事件、动作与外部状态；不把未知结果直接当失败重做写入 |
| `test:acceptance` 返回失败 | 当前完整清单仍有未验证项；查看具体清单，不能用组件测试通过替代 |
