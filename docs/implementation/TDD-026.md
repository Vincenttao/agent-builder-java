# TDD-026：Runner 重启后的历史制品恢复

日期：2026-10-22。状态：历史发布恢复与一次 Docker 业务冒烟通过；TD-15 累积验收仍未完成。

## 问题

Runner 镜像升级会改变内置 Java Bridge JAR 的摘要。重启后，历史发布仍固定引用旧 JAR；Artifact Registry 只识别当前默认 JAR 和带外部描述文件的生成组件，导致旧基础模板被报为 `ARTIFACT_NOT_FOUND`。即使 Runner 能恢复，服务端验收绑定也曾把任何非当前默认摘要视为验证依赖变化。

## TDD 实施

- 在 Runner Artifact Registry 中，缺少外部描述文件时只允许按内容摘要寻址的 JAR 进入旧模板识别；先校验文件摘要及非符号链接，再检查固定 Bridge 归档条目，并拒绝带生成组件标记的 JAR。未知摘要、被篡改字节和生成组件缺少描述文件仍失败关闭。
- 生成组件描述文件继续校验自身摘要、artifactDigest 和 SDK 摘要。SDK 可以是旧版本，但必须能从 Registry 校验并分类为不可变 assembled-template，因此旧候选可继续使用其构建时固定的 SDK。
- 发布／候选绑定根据 Runtime 返回的制品类型和内容摘要核对 assembled-template，不再要求其摘要等于新 Runner 的当前默认版本；生成组件仍需匹配 SDK、RuntimeSpec、快照和预期描述。
- 部署恢复用例覆盖运行时升级后旧模板及旧 SDK 生成组件的注册识别；绑定用例确认旧模板可匹配、模板不能冒充生成组件。
- 部署冒烟脚本并发读取各 Draft 的发布概览，避免 Draft 数量增大时顺序查找挤占运行验证时限。
