# TDD-023：受限 Tool 调用上限 Rail 生成

日期：2026-10-22。状态：已通过真实 DeepSeek/OpenCode 双角色生成 Rail 定义并构建候选 Bundle；Rail 超限行为验收及完整发布链路未完成。

## 目标

为设备只读 Agent 开发流程增加第一个可自动生成的 Rail 能力。模型只能填写已登记 Rail 模板的 JSON 参数；平台解析确认需求、校验定义并从快照 RuntimeSpec 派生候选规格，不接受模型提供任意代码或自行改写完整运行配置。

## 实现

- 将生成 Profile 升级为 `equipment-java@3`，范围加入 `rail`，开发角色获得精确路径 `rails/definition.json`。
- 新增 `tool-call-limit@1` 定义契约。当前只支持明确需求句式“每次运行最多 N 次工具调用”，N 为 1～20；歧义、多个上限、越界参数和未登记模板均拒绝。
- Runner 构建时按确认目标校验 Rail JSON，使用平台派生的有效 RuntimeSpec，并把定义、规格和摘要纳入不可变 Bundle。
- Server 登记 Candidate 时重新核对定义与原需求、从快照规格重算有效规格，再将 `specDigest` 交给 Runner 组合 JAR。候选后续测试和发布继续使用 TDD-022 已建立的规格绑定链路。
- OpenCode 开发提示明确 Rail 只写 JSON 定义，不生成 Rail Java Hook；运行时 Hook 仍来自受信任的固定 SDK Bridge。
- 真实双角色任务 `28696a98-867e-4f71-b25a-400867872304` 已将“每次运行最多 3 次工具调用”生成成合法定义，并在 Bundle 的 RuntimeSpec 中登记 `tool-call-limit@1:3`。Tester、Developer 均完成，Bundle、JAR 与定义摘要可追溯，详情见 [实时生成证据](evidence/TDD-023-live-rail-generation-28696a98-867e-4f71-b25a-400867872304.json)。

## 验证

- PostgreSQL 候选及开发集成测试通过：7 项；新增候选集成场景检查自然语言中的 3 次上限进入 Candidate RuntimeSpec，并校验其摘要传给制品组合器。
- 后续单独重跑候选集成：4 项通过。
- `corepack.cmd pnpm typecheck`：通过。
- 真实 DeepSeek/OpenCode 双角色生成：成功构建受限 Rail 候选 Bundle；这只证明定义生成和规格绑定，不代表业务行为验收。

## 未覆盖项

- Tester 目前仍只生成固定基线计划，没有专门的 Rail 边界场景；候选集成仅证明规格绑定，不证明超过上限时工具调用实际被阻止。
- 尚未用生成型 Candidate 完整跑 TestDeployment、Rail 边界执行、发布及发布冒烟链路。
- Skill 生成仍限于现有设备查询模板；没有支持任意底层业务接口的 Skill 自动包装。
- 此增量不覆盖任意 Rail/Tool/Agent 生成、写场景自动生成或沙箱。
