# TDD-043：真实写后超时崩溃的验收收敛

日期：2026-10-22。状态：NF-01 的“崩溃后不重放外部写”和自动退役分支通过本地隔离 Docker 验证；完整 TD-15 仍未通过。

## TDD-041/042 后续发现

TDD-042 解决了“PID 已退出但部署无法退役”。Docker 复验随后发现第二个恢复问题：Runner 再启动时，已经终结为 `interrupted` 的执行未再次进入 `restartUnsafeDeployments`，所以 Runner 又拉起了原部署 JVM。与此同时，执行日志将 `interrupted` 视为活动执行，阻止 `/deployments/:id/retire`，导致清理继续停在 `stopping`。

测试先行后作如下修复：

- `ExecutionJournal.initialize` 每次启动都把已持久化的 `interrupted` 执行对应部署加入恢复隔离集合；后续 Runner 启动不会重新拉起该 JVM。
- `hasActiveDeployment` 不再把已终结的 `interrupted` 执行当作活动请求。退役仍受 DeploymentManager 的 PID 存活检查保护：PID 存活或缺失时拒绝停止，PID 明确不存在才确认 `stopped`。
- TestDeployment 退役成功时清空先前的 `TEST_STOP_UNCONFIRMED` 诊断，避免已停止记录保留误导性失败信息。
- 故障验收脚本在 App 重启后重新建立管理会话，并等待验证报告完成和测试部署停止；报告区分“运行中断”与“不重复写入安全断言通过”。

## 验证证据

隔离 Docker 项目 `agent-builder-td15-nf01` 使用新构建的 App／Runner 镜像、独立 Postgres／Runner 数据卷及宿主端口 18080。主演示 `agent-builder-platform` 未升级，`/health/ready` 仍返回 `ready`。

固定 `equipment-workorder@1` 八项验证最终生成报告：TC-001～TC-007 通过；TC-008 因预期业务结果为 `succeeded`、而 SIGKILL 后真实 Run 为 `interrupted`，故总体报告为 `failed`。TC-008 的其它七项断言全部通过：审批前零写入、动作成功、写调用一次、业务状态一笔、有效决定一次、参数绑定正确、幂等键核对通过。Mock 记录 `work-order-create` 一次，业务工单只有一笔。Runner 执行日志和 Run 均为 `interrupted`；经隔离确认后部署最终为 `stopped`，无重复写入。

这是故障安全验收，不是故障后继续完成业务任务的验收。TC-008 的失败是诚实地反映被强制中断的 Run，不能改成成功；当前证明的是平台保留中断状态、没有重放业务副作用且能完成资源退役。详细记录见 [复验报告](evidence/TD15-NF01-active-write-restart-retest.json)。

此前第一次故障脚本因 App 重启后使用失效的内存会话而未能写出报告。此问题已修复；本轮报告从隔离 Postgres、Runner journal、部署状态和 Mock 控制状态中采集，并与候选绑定的八场景报告核对。故障脚本 `node --check` 通过。
