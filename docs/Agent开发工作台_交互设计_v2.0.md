# Agent 开发工作台交互设计 2.0

日期：2026-10-24。依据：[PRD 2.0](Agent开发工作台_PRD_v2.0.md)。本版已提供[可点击设计稿](developer-prototype-v2/开发工作台2.0.html)与[演示说明](developer-prototype-v2/README.md)，只代表第一阶段交互交付。

## 1 两种用户、两个工作区

| 角色 | 默认入口与导航 | 编辑对象 | 交付对象 |
| --- | --- | --- | --- |
| 平台开发者 | 范式工程、公共能力、开发 Skill、模板发行、联合诊断 | 公开 API/SPI 下的范式与接线、Rail/Tool、开发 Skill、开放契约 | 固定版本的范式、开发 Skill 与开发模板 |
| 场景开发者 | 我的应用、开发模板；应用内为模板与编排、业务操作与连接、代码与场景扩展、联合调试、测试与交付 | 业务配置、已开放规则、业务 Skill、映射脚本与局部扩展 | 固定场景应用及企业 CI/CD 交接材料 |

顶部角色切换仅用于演示两种视角。真实产品从用户身份和项目授权决定工作区；前端隐藏按钮不能代替后端或工具限制。切换角色不改写已有应用、运行或候选。

页面采用左侧角色导航、中央工作对象、右侧 Coding Agent 的布局。代码入口始终可达；Coding Agent 负责依据范式开发 Skill 辅助编排和修改，不把开发能力限制为聊天。

## 2 范式交接流程

平台方查看 MOA 的意图/任务/操作与终结机制，编辑公开契约及开发指导。Coding Agent 的“开放资格校验”建议同时影响契约与场景开发 Skill；查看差异、应用、检查后才发行模板。新模板不会自动升级已有场景应用。

页面主线为 **MOA 开发模板 → 创建场景应用 → 场景业务开发**。开发模板目录展示 MOA 的机制、工程骨架、扩展契约与开发指导。i豆是基于它创建的应用示例，不作为独立模板卡片。

创建表单先填写场景名称、目标，默认采用空白业务。用户可显式点击“填入 i豆演示示例”，加载本演示的业务资产和模拟数据；自定义场景保持空的业务 Skill、脚本和连接，不显示积分余额或兑换成功。模板来源与场景名称分别展示，导航和对话使用实际应用名称。

场景方固定 MOA 模板与开发 Skill 来源，再完成业务配置和局部修改。i豆完整演示需要资格校验扩展参数，首版 MOA 模板尚未开放，须先完成平台交接；不支持通过手工 JSON 绕过这个演示契约。真实产品必须在 API 和工程执行器实施同等约束。

开发 Skill 的知识来源固定到 `agent-solution` 的二开指南：MOA 快照 `1a92265cd`，`guides/docs-java` 快照 `68fcb1c31`。两者分别版本化，不能未经兼容验证混合 API。内容包括选择路径、工程分层、公开扩展、注册接线、允许范围和分层检查。

开发 Skill 给 OpenCode 使用；业务 Skill 随应用执行。设计稿分别展示两者，不把 `SKILL.md` 文件名相同当作用途相同。当前只展示指导文本，真实 Skill 包发现、装载与调用证据属于后续实现。

## 3 Coding Agent、编排与代码

1. 用户在当前工程提出目标。面板显示角色、应用/工程修订、开发 Skill 和可修改范围。
2. Agent 提出编排与文件差异。用户可查看修改前后，应用前草稿保持原内容。
3. 应用差异时核对基础修订。手工保存后旧建议不可覆盖新文件，需要重新生成。
4. 编排视图与代码引用同一修订。手工代码未保存时，导航/应用建议被拦截，可保存或恢复当前文件。
5. 应用配置、代码、礼品变化生成新修订，旧运行快照和候选不被改写；旧检查失效。撤销形成新修订，需要重新检查。

图中只显示模板支持的业务操作关系，不承诺任意拖拽流程均可执行。自由 Python/Java 代码不会在浏览器运行，也不能靠图形显示或静态检查宣布验证成功。

## 4 联合调试与 Trace

调试直接从草稿保存快照，无需先固定交付候选。界面同时展示对话、业务步骤和当前执行依据。标准接口可成功查询；嵌套接口夹具使旧映射失败；修复后重新运行产生新快照，原失败保留。

确认与写操作使用独立状态：待确认、确认失效、拒绝、成功、结果未知。改变礼品/应用修订使原确认失效。未知结果先查询原交易，不允许重新提交；取消或拒绝不能被表述为撤销已经发生的交易。

| Trace 区域 | 场景开发者 | 平台开发者 |
| --- | --- | --- |
| 执行列表 | 当前应用的运行、修订和结果 | 联合诊断入口查看运行与问题 |
| 分步详情 | 业务步骤、输入输出、错误与脚本定位 | 增加 Span/父 Span 标识；真实产品再显示实际采集的跨服务关系 |
| 回放控制 | 播放、暂停、上一步、下一步、指定步骤 | 同样只读；不因平台角色而允许重放交易 |
| 缺失数据 | 真实产品标记未采样/截断/未记录 | 额外提示传播和版本兼容边界，不虚构因果 |

Core/Runtime 已具备 OTel 上报源码。后续工作台主要接查询与版本关联；OTLP 接收、观测存储查询和业务事件保存需分别讨论。只读回放消费保存的数据，不是重运行或断点恢复。当前 Trace、Span、时间及载荷全部为模拟。

## 5 测试与企业交付

示例检查验证当前草稿，失败明确列出。通过后固定演示候选；修改草稿使当前交接按钮失效，旧候选仍可预览。下载内容固定到候选，不偷偷带入后续草稿修改。

页面区分目标交付包结构、JSON 设计清单与企业交接预演。当前不生成 JAR、不执行 CI、不真正停止工作台。后续真实产品必须在已验证应用包上证明：停止工作台及专用代理后，导出服务仍可独立完成业务。

## 6 分阶段落实

- DEMO-01：本版双角色静态网页，浏览器本地模拟即可；7 组交互检查与真实业务验收分开。
- DEV-02：先讨论本机 Node.js + OpenCode + Java 方案，再实现场景开发者的界面和后端；平台供给可先固定。
- FULL-03：先讨论方案，再补平台工程、公共能力、开发 Skill/模板发行及真实双角色协作。

本轮不启动 DEV-02/FULL-03，不部署新 Runtime 或观测服务。Demo 可直接打开 HTML 或使用 Node 静态服务，不以 Docker 作为前置条件。
